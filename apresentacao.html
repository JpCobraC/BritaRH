widgets Deploy do Frontend (Next.js) na Vercel

Estrutura de Hospedagem do Frontend

O frontend Next.js 14 foi hospedado diretamente na plataforma **Vercel** por meio da integração contínua vinculada à branch de produção do repositório. O diretório raiz configurado na Vercel é a pasta frontend/. A compilação é realizada automaticamente com otimização estática nativa do Next.js.

A criptografia das sessões de usuário (cookies HTTP-only) e as integrações de API usam as credenciais de ambiente injetadas no console da Vercel (como os segredos e URLs do NextAuth v5 e do Google Cloud Console).

Controle de Estados e Sessões no Frontend

O frontend do Next.js utiliza **React Server Components (RSC)** por padrão. Interações dinâmicas (como o Wizard de candidatura em etapas e os painéis de formulários) são marcadas com a diretiva `"use client"` e orquestradas pelo `ApplicationWizardContext`.

A autenticação do usuário é realizada por meio do **NextAuth.js v5 (auth.ts)** utilizando o provedor externo Google OAuth. Após a validação com o Google, o token de sessão JWT criptografado em cookies é propagado nas chamadas subsequentes à API do backend.

Banco de Dados Neon PostgreSQL

Para armazenamento relacional dos dados, o sistema utiliza o **Neon PostgreSQL**. O Neon é um banco de dados relacional serverless baseado em nuvem, otimizado para cargas variáveis e com suporte de recursos como branching de dados para testes.

Conexão Segura em Produção

A integração do backend Python FastAPI com o banco de dados é feita de maneira assíncrona utilizando as capacidades do framework **SQLAlchemy 2.x** em conjunto com o driver assíncrono **asyncpg**.

Formato da URL de Conexão: postgresql+asyncpg://neondb_owner:npg_iY6cXD3UOhZB@ep-mute-frog-ac62mp15-pooler.sa-east-1.aws.neon.tech/neondb?ssl=require

A diretiva ?ssl=require força o cliente de banco de dados a exigir túnel encriptado SSL, evitando ataques de Man-in-the-Middle e interceptação de dados sensíveis na comunicação entre a API FastAPI e o banco.

Construção de Imagem Docker & DockerHub

Construção e Versionamento no DockerHub

O backend FastAPI foi empacotado em um container isolado de produção. A imagem Docker foi compilada a partir do Dockerfile na raiz do backend, recebendo uma tag semântica de versão, e enviada ao registro público do **DockerHub**. Isso permite que o Render puxe a imagem pronta sem necessitar de build local.

Comandos de Build e Versionamento Executados: 
# Build da imagem baseada no Dockerfile
docker build -t seu-usuario/britarh-backend:1.0.0 ./backend

# Envio do container pronto para o repositório DockerHub
docker push seu-usuario/britarh-backend:1.0.0

Verificação de Conformidade do Código

Dockerfile: Verificado

Utiliza a imagem de base leve python:3.12-slim para reduzir a pegada em disco e a superfície de ataque. Instala dependências de compiladores gcc e cabeçalhos de postgres, limpando em seguida os arquivos temporários do apt para otimização da imagem.

Prestart e Migrações: Verificado

O container utiliza o entrypoint de shell script scripts/prestart.sh. Ele é acionado antes de iniciar o uvicorn para executar o comando alembic upgrade head, garantindo que o NeonDB esteja sincronizado com o último schema.

Deploy do Backend no Render via Imagem Docker

Hospedagem e Execução da API no Render

A API do backend foi implantada no **Render** configurada como um **Web Service** baseado em imagem de container externa. O Render puxa a imagem compilada diretamente do repositório DockerHub (docker.io/seu-usuario/britarh-backend:1.0.0) e inicializa o container de forma automática em sua infraestrutura Linux.

A orquestração do Render cuida do ciclo de vida do container: injeta as 7 variáveis de ambiente necessárias (como a URL do banco NeonDB e segredos de JWT) e direciona as chamadas HTTP recebidas na URL pública para a porta interna exposta 8000.

Configuração de Portas e Healthcheck

Por padrão, o Dockerfile expõe a porta `8000`. O Render detectará automaticamente a porta exposta pelo container ou escutará a porta informada na variável `PORT`.

O Render realiza verificações de integridade automáticas (healthchecks). A API do backend BritaRH conta com a rota dedicada `GET /api/v1/health` que responde com status HTTP `200 OK` assim que o serviço está no ar e conectado de forma bem-sucedida ao NeonDB.

Armazenamento de PDF com Cloudflare R2

Mapeamento de Armazenamento no Cloudflare R2

Para o armazenamento persistente dos arquivos de currículos recebidos, o sistema utiliza o **Cloudflare R2** configurado com protocolo compatível com AWS S3. Foi criado um bucket privado denominado britarh-curriculos.

A comunicação com o R2 é validada usando chaves de API S3 privadas do Cloudflare (Access Key ID e Secret Access Key) que concedem acesso restrito de escrita e leitura de objetos. Para permitir a visualização correta do PDF na interface, foram injetadas regras de CORS no bucket R2 liberando chamadas originadas do domínio do frontend Vercel.

Verificação do Código de Integração

Compatibilidade do StorageService

A classe StorageService (escrita no arquivo backend/app/services/storage.py) utiliza a biblioteca oficial da AWS boto3.

Como o Cloudflare R2 possui compatibilidade nativa com o protocolo S3, a integração funciona de forma nativa apenas configurando o parâmetro endpoint_url apontando para a R2 do Cloudflare.

MAPPING DE ENDPOINT CLOUDFLARE R2
https://<cloudflare-account-id>.r2.cloudflarestorage.com
