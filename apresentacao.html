Contexto de Software e Domínio do Sistema

O **BritaRH** foi projetado para informatizar de ponta a ponta o pipeline de recrutamento e triagem de candidatos. O objetivo é eliminar o armazenamento desnecessário de dados de candidatos e o processamento em lotes não estruturados de currículos. A solução unifica a candidatura, a avaliação teórica e o envio de documentos em um processo linear e assíncrono.

O sistema é categorizado como uma aplicação de arquitetura desacoplada (monorepo com front e back isolados). As regras corporativas estipulam que dados sensíveis de candidatos não selecionados devem ser apagados definitivamente de forma segura ao fechar o processo seletivo (princípio do expurgo e minimização de dados da LGPD).

layers Clean Architecture no Backend

O backend segue regras restritas para o fluxo de dados em sentido unidirecional em camadas concêntricas. O objetivo é isolar completamente o núcleo de regras de negócios de frameworks de comunicação e banco de dados:

1. Camada de Domínio (Models)

Contém as definições puras das entidades da regra de negócio (ex: User, Job, Question, Application). É totalmente independente de frameworks externos ou bibliotecas do banco de dados.

2. Casos de Uso (Services)

Implementa a lógica central de negócio (ex: cálculo de pontuação nos testes, verificação de e-mails em whitelist, e o purgador assíncrono para expurgo definitivo de dados).

3. Adaptadores (API Routers & Schemas)

Converte dados de entrada e saída. Roteadores FastAPI expõem recursos REST HTTP e Schemas Pydantic v2 validam e tipam as requisições de forma estrita.

4. Infraestrutura (Database & Storage)

Conectores físicos. Configurações de conexão assíncrona SQLAlchemy + Alembic para o PostgreSQL e provedor S3 MinIO para armazenamento de currículos.

security Segurança, Sanitização & Proteção de Vulnerabilidades

Autenticação e Autorização JWT

O sistema baseia-se em um modelo JWT simétrico de segredo compartilhado. O cabeçalho da requisição é inspecionado e validado por Middlewares de Dependência do FastAPI (`deps.get_current_user`). Rotas do painel admin de recrutadores exigem adicionalmente a validação da role `recruiter` contida no payload do token.

Prevenção a Injeção de Código (SQLi e XSS)

Para mitigar vulnerabilidades clássicas como SQL Injection, a aplicação utiliza parametrização de consultas via ORM SQLAlchemy 2.x com queries assíncronas nativas. No frontend, dados de usuários renderizados dinamicamente passam pelo processo de escape de caracteres nativo do Next.js (RSC).

Upload Seguro de Arquivos

O upload de currículos em formato PDF é realizado diretamente para o storage via URLs pré-assinadas com validade temporal curta (reduzindo a superfície de exposição). O backend valida rigorosamente o tipo MIME (`application/pdf`) e o tamanho máximo do buffer (5MB) para barrar uploads maliciosos.

Cabeçalhos de Segurança HTTP (Headers)

Middleware customizado no backend adiciona cabeçalhos protetivos obrigatórios a todas as respostas:

  • X-Content-Type-Options: nosniff
  • X-Frame-Options: DENY (evita clickjacking)
  • Strict-Transport-Security (HSTS forcing HTTPS)
  • X-XSS-Protection: 1; mode=block

person Ciclo de Vida da Candidatura (Candidato)

1 Google Login / Onboarding: Autenticação via conta externa. Caso o usuário não tenha o registro na base interna de dados, a interface aciona um formulário complementar exigindo CPF e data de nascimento.
2 Seleção de Vaga: O frontend consome dinamicamente o endpoint `GET /api/v1/jobs` buscando vagas ativas. O candidato seleciona a vaga desejada.
3 Formulário de Perfil (Wizard - Passo 1): Cadastro de histórico profissional estruturado. As informações são guardadas localmente no contexto do componente React (`ApplicationWizardContext`) antes da submissão unificada.
4 Avaliação Técnica (Wizard - Passo 2): Aplicação do questionário. Ao enviar as respostas, o backend valida as opções marcadas contra as alternativas corretas gravadas na tabela `questions` e calcula a pontuação (`score`).
5 Upload & Linkagem (Wizard - Passo 3): O frontend solicita uma URL de upload pré-assinada (`POST /api/v1/storage/presigned-url`). O arquivo PDF do currículo é enviado diretamente do navegador do usuário para o bucket S3 seguro, e a URL final é atrelada à tabela `applications`.

supervisor_account Ciclo Administrativo de Gerenciamento (Recrutador)

1 Validação de Credencial Admin: O sistema inspeciona se o e-mail do recrutador existe na tabela `recruiter_whitelist`. Caso sim, o papel de usuário logado assume o perfil administrativo de `recruiter`.
2 Construção de Vagas e Testes: Pelo painel administrativo, o recrutador insere título, requisitos e as questões de múltipla escolha. O backend cria registros sincronizados em `jobs` e `questions` em uma transação ACID atômica.
3 Avaliação dos Candidatos: O recrutador acessa o painel de candidaturas por vaga. O sistema consome `GET /api/v1/recruiter/jobs/{id}/applications`, que retorna a lista de candidatos classificados de forma decrescente pela pontuação obtida na avaliação técnica.
4 Homologação da Contratação e Expurgo (Purge): No encerramento da vaga, o backend executa um purgador de banco (`DELETE` em cascata) que remove permanentemente (Hard-delete) todos os registros associados à vaga (candidatos cadastrados e dados de aplicações) para garantir a segurança dos dados pessoais.

cloud Configuração de Hospedagem em Produção

A implantação do BritaRH na nuvem foi estruturada de forma distribuída para garantir escalabilidade e otimização de custos:

Hospedagem do Frontend (Next.js)

O frontend está publicado na **Vercel** com integração contínua (CI/CD) ativada diretamente pela branch `main`. A plataforma garante certificados SSL automatizados e distribuição global através de redes de entrega de conteúdo edge.

Hospedagem do Backend (FastAPI)

A API do backend está implantada no **Railway.app** ou **Render.com**. O deploy é acionado automaticamente através da análise do arquivo `Dockerfile` localizado no diretório `/backend`, encapsulando o servidor ASGI Uvicorn em ambiente Linux isolado.

Banco de Dados PostgreSQL de Produção

Hospedado no banco relacional serverless **Neon.tech** ou no add-on gerenciado do **Railway**. A string de conexão contém a diretiva `sslmode=require` para garantir a criptografia em trânsito de todos os dados do banco de dados.

Object Storage para Arquivos (Currículos)

O sistema local utiliza o MinIO. Em ambiente de produção, este é substituído por um bucket compatível com S3 (ex: **Cloudflare R2** ou **Backblaze B2**), garantindo custos mínimos de armazenamento e alta durabilidade física.
