Visão Geral: Clean Architecture no Frontend Clean Arch

O frontend do BritaRH é estruturado seguindo os princípios de Clean Architecture, separando regras de negócio conceituais da UI e da infraestrutura HTTP.

As camadas são rigorosamente isoladas de forma que a lógica central do cliente permaneça imune a mudanças tecnológicas (como bibliotecas HTTP, caches locais e APIs externas).

A Regra da Dependência

Dependências de código apontam apenas para dentro. O Domínio não conhece as bibliotecas HTTP (openapi-fetch) ou o sessionStorage do navegador. A Apresentação consome a Aplicação, que consome o Domínio.

Fluxo de Camadas

  • Domínio: Entidades TypeScript puras, regras de validação síncronas e contratos dos repositórios.
  • Aplicação (Casos de Uso): Fluxos e orquestrações de dados no client-side (ex: submissão de candidaturas).
  • Infraestrutura (Dados): Clientes HTTP (apiClient), sessionStorage, adaptadores/mapeadores de dados e chamadas externas.
  • Apresentação: Componentes visuais Next.js (App Router), hooks customizados, views e contexts.

Domínio: Entidades & Value Objects Domínio

A camada de Domínio representa as regras de verdade conceitual do negócio no client-side. É modelada com tipos e interfaces puros do TypeScript, livre de dependências de UI (React) ou bibliotecas HTTP.

  • Entidade: Objeto com identidade única através do tempo.
    Ex: O objeto Job (Vaga) possui ID único (string) e estado.
  • Value Object / Contratos de Tipo: Objetos/Tipos imutáveis que definem campos conceituais e garantem consistência estrutural.
    Ex: ApplicationProfile com regras de validação síncronas de email e nome.

Domínio: Erros & Repositórios (Contratos) Domínio

Para blindar as regras de negócios de contaminações externas, o Domínio define suas próprias **Exceções** e **Contratos de Persistência** (Interfaces de Repositório).

  • Erros de Domínio: Exceções específicas em TypeScript/JavaScript que validam regras de negócio antes de realizar submissões, tratadas pela camada visual.
  • Interfaces (Portas): Interfaces TypeScript (`IJobRepository`) que declaram as assinaturas necessárias, desacopladas de detalhes de rede e transporte.

Aplicação: Casos de Uso (Use Cases) Aplicação

A camada de **Aplicação** orquestra o fluxo de dados vindos da apresentação e gerencia as regras de negócio client-side.

  • Desacoplamento: O Caso de Uso depende apenas de entidades de domínio e interfaces abstratas de repositório.
  • Validação Conceitual: Executa as regras de validação do domínio no cliente antes de realizar chamadas de rede.
  • Responsabilidade Única: Cada classe executa uma ação de negócio discreta (ex: `SubmitApplicationUseCase`).
frontend/src/domain/usecases/GetJobsUseCase.ts
import { IJobRepository } from "../repositories/IJobRepository";

export class GetJobsUseCase {
  constructor(private jobRepository: IJobRepository) {}

  async execute(page?: number, size?: number) {
    return this.jobRepository.listOpenJobs(page, size);
  }
}
frontend/src/domain/usecases/SubmitApplicationUseCase.ts
export class SubmitApplicationUseCase {
  constructor(private applicationRepository: IApplicationRepository) {}

  async execute(
    jobId: string,
    candidateEmail: string,
    profileData: ApplicationProfile,
    score: number,
    file: File,
    message?: string
  ): Promise<Application> {
    if (!profileData.fullName || profileData.fullName.length < 3) {
      throw new Error("O nome completo deve conter pelo menos 3 caracteres.");
    }
    if (file.type !== "application/pdf") {
      throw new Error("Apenas arquivos PDF são aceitos.");
    }
    if (file.size > 5 * 1024 * 1024) {
      throw new Error("O currículo deve ter no máximo 5MB.");
    }
    return this.applicationRepository.submitApplication(
      jobId, candidateEmail, profileData, score, file, message
    );
  }
}

Infraestrutura: HTTP & Injeção de Dependências Infra

A camada de **Infraestrutura** resolve a comunicação externa (HTTP, cookies, storage) implementando as interfaces exigidas pelo Domínio.

  • HTTP Client: Configurado com `openapi-fetch` para typagem ponta a ponta dos schemas OpenAPI expostos pelo backend.
  • Injeção de Dependência (DI): Instanciação dos repositórios concretos e injeção síncrona nos construtores dos use cases dentro do ciclo de renderização do React.

Infraestrutura: Repositórios & Storage Infra

A persistência de rede e de cache temporário é tratada inteiramente por adaptadores e APIs de storage do navegador.

  • Implementação de Repositórios: Realiza chamadas REST com `FormData` para upload de PDF e mapeia DTOs brutos para Entidades do Domínio.
  • Storage local (sessionStorage): Persistência de rascunhos de fluxo multi-etapas no navegador para evitar perdas acidentais em F5.
frontend/src/data/repositories/ApiJobRepository.ts
export class ApiJobRepository implements IJobRepository {
  async getJobById(id: string): Promise<Job | null> {
    const response = await apiClient.GET("/api/v1/jobs/{job_id}", {
      params: { path: { job_id: id } }
    });
    if (response.error || !response.data) return null;
    
    // Mapeia DTO backend para Entidade de Domínio
    const rawJob = response.data;
    return {
      id: rawJob.id,
      title: rawJob.title,
      area: rawJob.area,
      status: rawJob.status as any,
      questions: rawJob.questions?.map((q: any) => ({
        id: q.id,
        text: q.text,
        options: q.options as [string, string, string, string],
        correctIndex: q.correct_index,
      }))
    };
  }
}

Apresentação: Hooks Customizados Frontend

Os **Hooks Customizados** do React servem para encapsular a lógica de estado, chamadas de Casos de Uso e ciclo de vida visual de carregamento.

  • useJobs: Abstrai a listagem de vagas delegando ao `GetJobsUseCase` e gerenciando estados de `loading`, `error` e listagem.
  • useSubmitApplication: Gerencia o envio de candidaturas orquestrando a injeção do repositório no `SubmitApplicationUseCase`.
frontend/src/presentation/hooks/useSubmitApplication.ts
export function useSubmitApplication() {
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);
  const [success, setSuccess] = useState(false);

  const submit = async (jobId: string, email: string, profile: ApplicationProfile, score: number, file: File, msg?: string) => {
    setLoading(true); setError(null); setSuccess(false);
    try {
      const repo = new ApiApplicationRepository();
      const usecase = new SubmitApplicationUseCase(repo);
      const result = await usecase.execute(jobId, email, profile, score, file, msg);
      setSuccess(true);
      return result;
    } catch (err: any) {
      setError(err.message || "Erro ao enviar");
      throw err;
    } finally {
      setLoading(false);
    }
  };
  return { submit, loading, error, success };
}

Qualidade: Testes Unitários com Vitest Garantia de Qualidade

Testes Unitários garantem a estabilidade de regras de lógica de negócios e formatadores client-side. São velozes e executados sem acessar rede.

  • Vitest: Test runner ultra rápido integrado ao bundler do frontend para execução ágil com mocks.
  • Use Cases: Testar se invariantes conceituais do domínio (como tamanho máximo do currículo e obrigatoriedade de campos) são respeitados.
frontend/src/__tests__/usecases.test.ts
import { describe, it, expect, vi } from "vitest";
import { SubmitApplicationUseCase } from "../domain/usecases/SubmitApplicationUseCase";

it("should throw error if file size is over 5MB", async () => {
  const mockFile = new File(["dummy"], "c.pdf", { type: "application/pdf" });
  Object.defineProperty(mockFile, "size", { value: 6 * 1024 * 1024 }); // 6MB
  const mockRepo = { submitApplication: vi.fn() };
  const usecase = new SubmitApplicationUseCase(mockRepo);

  await expect(usecase.execute("v-1", "j@d.com", profile, 80, mockFile))
    .rejects.toThrow(/máximo 5MB/);
});
